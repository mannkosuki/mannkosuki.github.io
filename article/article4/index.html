背景介绍

在 bmcweb 的异步编程中，经常会遇到以下两种情况，

1、链式调用

每一个异步任务都依赖于上一个异步任务的执行结果，这样当嵌套层数过多时，代码格式上较复杂，阅读困难。

dbus::utility::getProperty<T>(
    service, path, interface, property, 
    [variables](const boost::system::error_code& ec, const T& prop) {
        ...
        dbus::utility::getProperty<T>(
            service, path, interface, property, 
            [variables](const boost::system::error_code& ec, const T& prop) {
                ...
                dbus::utility::getProperty<T>(
                    service, path, interface, property, 
                    [variables](const boost::system::error_code& ec, const T& prop) {
                        ...
                        dbus::utility::getProperty<T>(
                            service, path, interface, property, 
                            [variables](const boost::system::error_code& ec, const T& prop) {
                            ...              
                        });
                        ...           
                });
                ...  
        });
        ...
});

2、异步任务收敛

某一个异步任务需要等待多个异步任务的执行结果，在获取所有执行结果后方能继续后续任务。

task1()
{
    dbus::utility::getProperty<T>(
        service1, path1, interface1, property1, 
        [variables](const boost::system::error_code& ec, const T& prop) {
            ...
    });
}

task2()
{
    dbus::utility::getProperty<T>(
        service1, path1, interface1, property1, 
        [variables](const boost::system::error_code& ec, const T& prop) {
            ...
    });
}

// 执行前置条件：task1和task2全部执行完成
taskConvergence()
{
    ...
}

taskEntry()
{
    task1();
    task2();
    taskConvergence();
}

解决方法

1、将异步任务封装成函数

对于链式调用的多层嵌套，可以通过将不同的异步任务封装成函数的形式，解决代码格式上的问题，更加方便阅读，缺点是需要额外封装函数，没有 lambda 表达式书写更方便。

taskStep4(const boost::system::error_code& ec, const T& prop)
{
    ...
    handle(ec, prop);
    ...
}

taskStep3(const boost::system::error_code& ec, const T& prop)
{
    ...
    handle(ec, prop);
    dbus::utility::getProperty<T>(
        service, path, interface, property, 
        [variables](const boost::system::error_code& ec, const T& prop) {
            taskStep4(ec, prop);
        });
    ...
}

taskStep2(const boost::system::error_code& ec, const T& prop)
{
    ...
    handle(ec, prop);
    dbus::utility::getProperty<T>(
        service, path, interface, property, 
        [variables](const boost::system::error_code& ec, const T& prop) {
            taskStep3(ec, prop);
        });
    ...
}

taskStep1(const boost::system::error_code& ec, const T& prop)
{
    ...
    handle(ec, prop);
    dbus::utility::getProperty<T>(
        service, path, interface, property, 
        [variables](const boost::system::error_code& ec, const T& prop) {
            taskStep2(ec, prop);
        });
    ...
}

dbus::utility::getProperty<T>(
    service, path, interface, property, 
    [variables](const boost::system::error_code& ec, const T& prop) {
        taskStep1(ec, prop);
});

2、共享指针处理回调收敛

对于需要异步收敛的场景，经常采用多个异步任务共同捕获同一个自定义容器对象的共享指针，并将收敛之后需要执行的任务注册到容器对象，在容器对象析构时执行回调函数的方式，这也是 asyncResp 的实现原理。

以下是一个自定义容器的实现

std::shared_ptr<AsyncBatchProcesser<int>> asyncBatchProcesser =
    std::make_shared<AsyncBatchProcesser<int>>([](std::vector<int>& data) {
        ....
        for (const auto& it : data)
        {
            handle(it);
        }
    });

dbus::utility::getProperty<T>(
    service, path, interface, property, 
    [asyncBatchProcesser](const boost::system::error_code& ec, const T& prop) {
        ...
        asyncBatchProcesser->data.emplace_back(data1);
    });

dbus::utility::getProperty<T>(
    service, path, interface, property, 
    [asyncBatchProcesser](const boost::system::error_code& ec, const T& prop) {
        asyncBatchProcesser->data.emplace_back(data2);
    });

3、协程——同步方式编写异步过程

协程的用法和线程类似，但是最本质的区别是，协程的调度是在应用层进行，线程的调度是由操作系统完成，协程更加的轻量，切换上下文开销更小。

注意！当前 bmcweb 编程中，GET 接口不允许使用协程方式实现异步。由于 GET 方法的 expand 操作会存在并发处理接口 hander 的场景，如果应用协程处理，存在大量协程挂起的情况对进程的影响未知。因此当前协程方式编码允许在 POST 与 PATCH 方法下并且数据请求存在链式依赖的情况下使用。

spawn 的方式创建协程

void spawn(
    boost::asio::io_context& ioc,
    Function&& function,
    boost::asio::yield_context yield = boost::asio::yield_context());
#include <iostream>
#include <boost/asio.hpp>
#include <boost/asio/spawn.hpp>
#include <chrono>

using namespace boost::asio;

io_context io;

void task1(yield_context yield) {
    steady_timer timer(io);
    try {
        timer.expires_from_now(std::chrono::seconds(1));
        std::cout << "Task1 started, waiting for 1 second..." << std::endl;
        timer.async_wait(yield);
        std::cout << "Task1 completed!" << std::endl;
    } catch (std::exception& e) {
        std::cerr << "Task1 Exception: " << e.what() << std::endl;
    }
}

void task2(yield_context yield) {
    steady_timer timer(io);
    try {
        timer.expires_from_now(std::chrono::seconds(2));
        std::cout << "Task2 started, waiting for 2 seconds..." << std::endl;
        timer.async_wait(yield);
        std::cout << "Task2 completed!" << std::endl;
    } catch (std::exception& e) {
        std::cerr << "Task2 Exception: " << e.what() << std::endl;
    }
}

int main() {
    try {        
        auto start_time = std::chrono::steady_clock::now();  // 记录开始时间

        // 创建并启动两个协程
        spawn(io, task1, {});
        spawn(io, task2, {});

        std::cout << "Main: Coroutines started, running event loop..." << std::endl;
        io.run(); // 启动事件循环，处理异步操作

        auto end_time = std::chrono::steady_clock::now();  // 记录结束时间
        auto duration = std::chrono::duration_cast<std::chrono::milliseconds>(end_time - start_time);
        std::cout << "Main: Event loop finished. Total time: " << duration.count() << "ms" << std::endl;
    } catch (std::exception& e) {
        std::cerr << "Exception: " << e.what() << std::endl;
        return 1;
    }
    return 0;
}

基于事件驱动模型

为了减少回调函数的嵌套，以及更直观的理解多个回调任务收敛的过程，本文将介绍一种基于事件驱动模型的松耦合编程方法。

模型基于订阅-发布的形式，将不同回调任务之间去耦合，每个异步任务将自己的执行时机交给事件总线托管。每个异步任务需要处理事件总线传输过来的数据，并将自己执行之后的数据送到事件总线。

该模型的具体实现位于，G70/bmcweb/event_bus.hpp

bmcweb 编程注意点

1、在每个异步回调中都要捕获以值的形式捕获 asyncResp，为了保证回调执行完再返回 asyncResp，如果不使用 asyncResp 可以调用如下语句消除 unused 警告：
std::ignore = asyncResp;
2、跨域传递参数或者管理变量生命周期时，首推智能指针。例如多个 lambda 表达式中需要使用同一个变量，推荐封装成 shared_ptr 的形式使用。如果采用引用方式管理变量，很容易出现 coredump 问题。 
std::string eventId1 = genEventId("Test1");
std::string eventId2 = genEventId("Test2");

taskEntry()
{
    ...
    std::shared_ptr<nlohmann::json::object_t> jsonPtr =
        std::make_shared<nlohmann::json::object_t>();
    process(jsonPtr);
    asyncEventBus->addEventData(eventId1, "jsonPtr", jsonPtr);
    asyncEventBus->publish(eventId1);
    ...
}

asyncEventBus->subscribe(eventId1, [eventId1, eventId2](const async::EventDataMap dataMap){
    if (auto jsonPtrOpt = async::getEventData<std::shared_ptr<nlohmann::json::object_t>>(dataMap, eventId1, "jsonPtr"))
    {
        ...
        auto& jsonPtr = *jsonPtrOpt;
        process(jsonPtr);
        asyncEventBus->addEventData(eventId2, "jsonPtr", jsonPtr);
        asyncEventBus->publish(eventId2);
        ...
    }
});

asyncEventBus->subscribe(eventId2, [eventId2](const async::EventDataMap dataMap){
    if (auto jsonPtrOpt = async::getEventData<std::shared_ptr<nlohmann::json::object_t>>(dataMap, eventId2, "jsonPtr"))
    {
        ...
        auto& jsonPtr = *jsonPtrOpt;
        process(jsonPtr)
        ...
    }
});
3、每个捕获 asyncResp 的 lambda 表达式，需要保证该 lambda 表达式在将来一定会被回收，如果不回收则 asyncResp 无法被销毁，接口不会返回。
